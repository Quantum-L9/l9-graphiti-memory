## Status

Accepted

The decision takes effect when it merges to `main` under the product owner's
review. It binds exactly one ProductTopology candidate:

| Coordinate | Value |
|---|---|
| ProductTopology | `product-topology.yaml` |
| Topology digest | `sha256:03272dd6f7774149f125fa5c4d462f1a9c70c4f6ea27f9cd085bcdb78642fb6e` |
| Global authority | `Quantum-L9/.github@976eedb58358355919a7eb39b4c78bd52a54a102` |
| Global release contract | `l9.contract/product-release@1` |

The topology digest is the SHA-256 of the committed `product-topology.yaml`
bytes, including its inline L9 metadata header. If those bytes change
materially, this decision is stale and must be reissued for the new digest.
`tests/regression/test_product_release_governance.py` fails while the
committed topology digest differs from the digest recorded here and in
`release-work/product-release-binding.yaml`.

## Context

The repository already owned a mature memory architecture:

- one canonical `MemoryService` (ADR-002);
- server-derived caller identity (ADR-083);
- graph and semantic providers held as projections (ADR-013, ADR-063, ADR-084);
- a consumer-owned process lifecycle (ADR-001, ADR-065, ADR-067);
- Gate-only constellation dispatch (ADR-060).

It had no authoritative product contract in the global L9 topology vocabulary,
however. Its release machinery (`scripts/validate_release.sh`,
`.github/workflows/publish.yml`) proved artifacts but bound to nothing that
said what product was being released, which global release law applied, or
which evidence a release owed.

`Quantum-L9/.github` now publishes `l9.schema/product-topology@1`, the admitted
ProductKinds and archetypes, and the global release contract
`l9.contract/product-release@1`. A product consumes that law; it does not
restate it.

## Decision

1. **ProductKind is `dependency`.** The archetype is
   `l9.dependency-archetype/semantic-subsystem@1`.
   - Consumption is `local_composition`.
   - Deployment is `consumer_bound_artifact`.
   - The kind follows from the canonical consumption and deployment model, not
     from repository shape, package format or provider identity. The CLI,
     MCP, HTTP and Gate adapters are local surfaces of a composed package.
     They do not make the product a Node.
2. **`product-topology.yaml` is the authoritative product contract** for this
   repository. It encodes the accepted memory architecture.
   - Memory owns:
     - memory contracts, authorization policy and admission;
     - canonical persistence, lifecycle and retrieval semantics;
     - curation and receipts;
     - the SDK, CLI and MCP surfaces;
     - provider ports and projection semantics;
     - compatibility policy.
   - Memory does not own:
     - agent execution or world-model semantics;
     - cross-node or Gate routing;
     - consumer runtime identity or business-domain semantics;
     - provider, Cursor-Governance, Graphiti or Zep semantics.
   - Canonical memory persistence is authoritative product state. Graphiti and
     Zep state is derived projection state.
3. **Identity.** ProductIdentity and ReleaseIdentity are distinct and both
   apply.
   - The product has no independent RuntimeIdentity:
     `RuntimeIdentity(dependency_instance) = RuntimeIdentity(consumer)`.
   - It has no constellation identity.
   - Actor identity applies because memory writes are authorship. It is
     derived server-side and fails closed when unknown or ambiguous.
   - Surface identity does not apply, because transport parity (ADR-082) keeps
     every surface semantically identical.
4. **The ProductManifest is derived here, deterministically.** Global law
   names `l9-semantic-compiler` as its owner, but no such compiler exists, and
   release progression must not depend on one. The ProductManifest is
   therefore generated by `tools/assurance/generate_product_manifest.py`:
   - It reads this topology plus the pinned global semantics from a
     `Quantum-L9/.github` checkout, and copies nothing from either.
   - It evaluates all 17 `resolved_manifest_gate` conditions of
     `l9.schema/product-manifest@1` mechanically.
   - It writes `release-work/product-manifest.json`. That file records the
     generator's own digest as its `compiler_version` and carries a canonical
     `manifest_digest`.

   The manifest is never hand-authored. It is current only while its
   `source_topology.digest`, authority coordinates and generator digest match.
   An admitted global compiler, if one ever exists, supersedes this generator.
5. **`release-work/product-release-binding.yaml` is derived.** It is an
   execution and proof map, not product authority. It binds:
   - the global release contract, the authority revision and the topology
     digest;
   - the ProductManifest coordinate, its digest, its generator digest and its
     gate result;
   - the release identity source, `version.PACKAGE_VERSION`;
   - the validation and publication entrypoints and the proof entrypoints.

   It defines no second release contract and no new receipt family.
6. **Every release is governed by `l9.contract/product-release@1`.**
   - Validation, conformance and successful execution never admit a release.
   - Release admission is an explicit authority decision, bound to the exact
     frozen candidate (version, source revision, wheel sha256, sdist sha256).
   - Publication distributes only those admitted bytes.
7. **Consumer binding is separate from product release admission.**
   `Quantum-L9/Cursor-Governance` selects, installs, binds and proves an
   admitted release on its own side. That outcome never redefines this
   product's ReleaseIdentity.
8. **Material Unknowns stay explicit.** A requirement with no admitted global
   coordinate is recorded, never invented:
   - MU-001 (closed): a conformance profile for dependency or semantic-subsystem.
     `Quantum-L9/.github@976eedb58358355919a7eb39b4c78bd52a54a102` admits
     `l9.fixture-profile/core@1` and this topology consumes that coordinate.
     The derived ProductManifest therefore no longer fails
     `conformance_requirements_resolved` or
     `unresolved_hard_semantic_gaps_empty` for lack of that coordinate.
   - MU-002 (closed): technology coordinates for the Graphiti MCP and Zep
     provider realizations. `Quantum-L9/.github` admitted `graphiti-mcp` and
     `zep` (Semantic Foundation v3.12.0), and the topology's provider bindings
     consume them, so `provider_bindings_admissible` holds.

   The generator flips the gate to `pass` with no code change once the
   authority admits the remaining coordinate and the topology consumes it.

## Alternatives Considered

- **Classify as a Node**, because the package exposes MCP and HTTP servers.
- **Keep release governance implicit** in `validate_release.sh` and
  `publish.yml`.
- **Hand-author the ProductManifest locally** so release progression is not
  blocked.
- **Wait for `l9-semantic-compiler`** before any ProductManifest exists.

## Rejected Alternatives

- **Node:** rejected. The package has no independent runtime or constellation
  identity and its process lifecycle is consumer-owned. Process presence alone
  does not determine ProductKind.
- **Implicit governance:** rejected. It cannot show which global law, topology
  or manifest a release was validated against.
- **A hand-written ProductManifest:** rejected. A hand-written manifest would
  claim derivation it did not undergo. The repository generator derives it
  mechanically and records itself as the compiler.
- **Waiting for a compiler:** rejected. No compiler exists, and a release
  must not depend on an absent tool. Only the gate result governs progression.

## Invariants

- One ProductTopology per product. It is the authoritative product contract.
- A ProductManifest and the release binding are derived and never authoritative.
- No `l9.*` identifier, conformance profile or receipt family is invented here.
- A topology change invalidates this decision until it is reissued for the new
  digest.
- Global release law is consumed and may be strengthened locally, never
  weakened.

## Consequences

- MU-001 is resolved by its global owner and consumed by this topology.
- Release progression still requires two things:
  - the ProductManifest derived from this topology passes the resolved-manifest
    gate;
  - an explicit release admission exists.
- The release proof set is derived from the topology, the manifest, the binding
  and the current implementation. It no longer comes from a hand-maintained
  blocker list.

## Security Impact

None at runtime. The topology states the existing secret, identity and
authorization boundaries (ADR-016, ADR-066, ADR-083) and adds no credential
path.

## Migration Impact

None. No code, schema, persisted data or public contract changes. The
topology, this ADR and the binding are new tracked files and are listed in the
release manifest.

## Validation Requirements

- `python tools/assurance/validate_product_topology.py --authority-root <Quantum-L9/.github checkout at the pinned revision>`
  passes. It reads global law from the checkout at run time and never copies
  it.
- `tests/regression/test_product_release_governance.py` passes. It checks that
  the topology digest, this decision and the release binding agree.
- `python tools/assurance/generate_product_manifest.py --authority-root <checkout> --check`
  passes. CI pins the authority checkout and runs both checks inside
  `scripts/validate_release.sh` through `L9_SEMANTIC_AUTHORITY_ROOT`.
- `bash scripts/validate_release.sh` passes.

## Rollback Conditions

Revert this ADR, `product-topology.yaml`, the release binding, the validator,
the ProductManifest generator and its output, and the governance test together,
then re-run explicit preparation. Roll back
if the global authority reclassifies the product kind or withdraws
`l9.contract/product-release@1`.

## Supersedes / Superseded By

Supersedes no ADR. It is superseded only by a later product-owner decision
bound to a new topology digest.

## Amendment — unresolved: centrally hosted remote consumption (2026-10-13)

**Decision date:** 2026-10-13 (campaign MEM-HTTP-DOC-01).
**Status of the question:** open. This amendment records a discrepancy. It
does not reclassify the product, edit `product-topology.yaml`, change the
topology digest above, or claim any admission.

ADR-038's 2026-10-13 amendment sets a target in which Cursor and Claude Code
agents consume canonical memory from one centrally hosted HTTPS service. The
accepted topology says something different:

| Accepted topology (`product-topology.yaml`) | Remote target |
|---|---|
| `consumption.model: local_composition` | agents on other machines invoke one shared service over the network |
| `forbidden_consumption_modes` includes `remote_invocation_as_canonical_consumption` | remote invocation is the intended canonical agent path |
| `deployment.runtime_boundary: consuming product process` | the runtime is a hosted service, not the agent client's process |
| RuntimeIdentity inherited from the consumer; no constellation identity | a long-lived service has health, readiness and a network identity of its own |
| `mcp_http` listed as a public entry mode of a locally composed package | the same adapter serves remote callers |

Global law (`Quantum-L9/.github` `semantics/product_kinds.yaml`) classifies by
canonical consumption and deployment model, never by process presence alone.
A `node` is `remote_invocation` plus `independent_runtime` and additionally
requires independent runtime identity, independent health and readiness,
canonical constellation communication, Gate-routed inter-product work and
runtime admission. A `dependency` is `local_composition` plus
`consumer_bound_artifact` and requires a consumer-owned process lifecycle.

Two readings are possible. Neither is adopted here:

1. **Dependency retained, consumer-owned hosting runtime (candidate).** The
   hosted service is the runtime of a *consuming* product that composes this
   package locally and owns process lifecycle, runtime identity, health and
   deployment. This package stays a `dependency`. The owner must still decide
   whether agents calling that host's MCP endpoint is
   `remote_invocation_as_canonical_consumption` of *this* product, which the
   topology forbids, and must name the consuming product that owns the host.
2. **Node.** Requires the global Node gates above, which the MCP HTTP adapter
   does not meet — in particular canonical constellation communication and
   Gate-routed inter-product work — plus a new topology, a new digest and a
   reissued decision.

Until the product owner resolves this through the process this ADR defines:

- the accepted topology and its digest stay exactly as recorded above;
- no document may describe the hosted remote service as an admitted product
  topology, a Node, or an approved remote canonical consumption mode;
- the HTTP implementation campaign may build and qualify the transport, but
  its outcome does not settle the classification.

## Amendment — 3.0.0 hosting and the unresolved classification (2026-10-14)

**Decision date:** 2026-10-14 (campaign MEM-DOC-3.0, documentation only).
**Status of the question:** still open. This amendment sharpens the
2026-10-13 record against the global law at one pinned revision. It does not
edit `product-topology.yaml`, its digest, its provenance pins, the release
bindings or any global semantic file, and it admits nothing.

### The desired deployment

Memory 3.0.0 is intended to run as one centrally hosted service on the
operator-controlled Hetzner C1 environment, serving canonical memory to
authorized agents on other machines over authenticated HTTPS MCP (ADR-038,
2026-10-14). That is the deployment the operator wants. Its canonical
classification is a separate question, and this ADR keeps them separate.

### The discrepancy, at the pinned revision

Global law read at `Quantum-L9/.github@976eedb58358355919a7eb39b4c78bd52a54a102`,
the revision this topology's `provenance.authority_ref` and CI pin. At
`.github` `main@f9993ed` (2026-10-14) `semantics/product_kinds.yaml` and
`semantics/dependency_archetypes.yaml` are unchanged, and the changes to
`vocabulary.yaml`, `authority_model.yaml` and `architecture_patterns.yaml`
concern strategic planning and projection patterns, not the consumption and
deployment modes cited here. `validate_product_topology.py` against that newer
revision fails on the topology's pins, not on this question.

| Global rule (`.github@976eedb`) | Hosted 3.0.0 deployment |
|---|---|
| `product_kinds.yaml`: only `node` and `dependency` are admitted kinds | no hosted-service or hosted-dependency kind exists |
| `dependency` forbids `remote_invocation_as_canonical_consumption` and `independent_constellation_identity_as_dependency` | agents on other machines invoke the service as their canonical memory path |
| `dependency`: `RuntimeIdentity(dependency_instance) = RuntimeIdentity(consumer)` | the hosted process has its own health, readiness and network identity |
| `architecture_patterns.yaml` `l9.pattern/dependency-package@1`: `Lifecycle(package_instance) ⊆ Lifecycle(consumer)`; forbids `separate_runtime_identity_without_explicit_node_binding` | the service's lifecycle is the host's, not an agent client's |
| `node` requires `independent_runtime_identity`, `independent_health_and_readiness`, `canonical_constellation_communication`, `gate_routed_inter_product_work` and `runtime_admission`, through `runnable-node@1` and `semantic-core-gate-adapter@1` | the MCP HTTP adapter speaks MCP to agents, not TransportPacket through Gate, and no runtime admission exists |

### Candidates, unchanged in substance

- **Candidate A — consumer-owned hosting runtime.** An already authorized
  consuming product composes this package locally and owns the C1 process,
  its runtime identity, health, readiness and deployment; this package stays
  a `dependency`. It holds only if (a) that consuming product is named and its
  canonical ownership of the runtime is resolved, and (b) the authority over
  `remote_invocation_as_canonical_consumption` rules that agents calling the
  host's MCP endpoint is not that forbidden mode, or changes the rule. The
  sources read for this amendment name no such consuming product, and the
  pinned global law has no hosted-dependency concept, so (a) and (b) are both
  unmet today.
- **Candidate B — independent Memory Node.** Memory becomes a separately
  admitted `node`. That needs every Node requirement in the table, including
  Gate-routed TransportPacket communication and runtime admission, plus a new
  topology revision, digest and product-owner decision. An HTTPS server alone
  does not satisfy it.

GAR's stated preference is to reuse an existing authorized hosting boundary
if one lawfully satisfies the requirements, rather than to create a Node only
because the process is remotely reachable. This amendment records that
preference and does not select either candidate.

### Owners and the narrowest decision needed

| Question | Owner |
|---|---|
| This product's topology and ProductKind | `product_semantic_owner` (`authority_model.yaml` `product_topology_authority`); for this product `l9-graphiti-memory:authority/memory-architecture` |
| Admission of a changed topology | `l9.authority/product-admission`, decided by the applicable target-class authority; `product_kind_change_is_material` (`lifecycle.yaml`) |
| Meaning of ProductKind, consumption and deployment modes, and whether a consumer-hosted runtime serving remote agents is `remote_invocation_as_canonical_consumption` | `Quantum-L9/.github` global semantics |
| C1 hosting runtime, if Candidate A | the consuming product that owns it |

The operator decision needed is: **choose Candidate A and name the consuming
product that owns the C1 runtime (and obtain the `.github` ruling in (b)), or
choose Candidate B and open Node admission.** Until then the accepted topology
and digest stand, no document may call the hosted service an admitted
topology, a Node, or an approved remote canonical consumption mode, and the
3.0.0 deployment is architecturally intended but canonically unclassified.
