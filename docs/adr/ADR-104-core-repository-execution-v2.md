# ADR-104: Core Repository Execution V2

**Date:** 2026-11-14
**Decision owner:** Quantum-L9 memory architecture
**Applies to:** the root `Makefile`, `Repo.mk` and `.l9/repo-workflow.json` of `Quantum-L9/l9-graphiti-memory`, as merged in pull request #120

This record states the decision merged in #120. It does not change the
release validation of ADR-101 or the file-structure law of ADR-099 beyond the
two top-level entries named below.

## Status

Proposed

The author of this change does not accept its own decision record. Merging
this record on the default branch by the decision owner accepts it; the index
status changes in that same merge.

## Context

`Quantum-L9/l9-ci-core` (Core) runs repository verification in `required`
mode for this repository; the required check is `Analyze (central Core)`. In
required mode a repository without a Repository Execution V2 contract fails
before any of its gates run. Before #120 this repository had no
`.l9/repo-workflow.json`, no root `Makefile` and no `Repo.mk`, and every pull
request, documentation-only ones included, failed with:

```
repository verification: FAIL (contract; required mode and .l9/repo-workflow.json absent)
```

The repository's executable gates were defined only by the `validate` job of
`.github/workflows/ci.yml` and by `scripts/validate_release.sh`.

Running those gates on Core's runner exposed three differences from CI's
`validate` job, each recorded in a commit of #120:

1. `tools/assurance/check_recursive_alignment.py` walked the whole checkout
   and judged the l9-ci SDK source that Core materializes under
   `.l9/runtime/` (commit `1fb1214`). Those bytes are Core's, not this
   repository's.
2. Core runs each phase as its own `make` process. A uv that `repo-setup`
   bootstrapped was not on PATH in the later `validate` process, so the
   installed-wheel fixtures fell back to `python -m pip`, which a
   uv-created venv does not carry (commit `591e244`).
3. Core checks out only the candidate revision at depth 1, with no
   `origin/main` ref, so the ADR-101 suite base resolved as
   `UNRESOLVED: base ref origin/main is not a commit here` and V-001 ended
   unknown (commit `96f6f3e`). CI's job has the base because it checks out
   with `fetch-depth: 0`.

## Decision

### The V2 contract

- `.l9/repo-workflow.json` holds exactly
  `{"schema": "l9.repo-execution/v2", "facade": "make-v1", "required_phases": ["setup", "validate", "check", "test"]}`.
- The root `Makefile` is Core's generated `make-v1` facade, byte-for-byte
  (generated by Core's `tools.l9_repo reconcile`; sha256
  `59d75892d7c8af83916187c5af612d2c9697741a68017265059567e4ea33cba6`). It is
  never edited here.
- Every repository recipe lives in `Repo.mk`. Its leaves reproduce CI's
  `validate` job in the job's order: `repo-setup` runs the job's locked
  `uv sync` with the same extras; `repo-check` runs `ruff check`, `mypy`, the
  active-memory public-API gate and the service-free assurance validators;
  `repo-test` runs the full pytest suite; `repo-validate` runs the suite
  base, check, the active-memory subsystem tests, then
  `scripts/validate_release.sh`.
- `tools/assurance/check_recursive_alignment.py` admits `Makefile` and
  `Repo.mk` as top-level entries in the allowlist ADR-099 retained.

CI is not rewired to call `make`; `ci.yml` stays the authority for hosted CI
and `Repo.mk` mirrors it.

### What `Repo.mk` and the alignment scan do so Core gets CI's result

- **The alignment scan judges only this repository's files.** In a git work
  tree it enumerates tracked files plus untracked files the repository's
  ignore rules admit, minus untracked files under the injected
  `.l9/runtime/` directory; a file the repository tracks there is still
  judged. Without a work tree it walks the tree as before, pruning
  `.l9/runtime` by exact path. No finding text is allowed or ignored.
- **A bootstrapped uv stays on PATH for every phase.** `repo-setup` installs
  uv into the untracked `build/uv-bootstrap` only when no uv is on PATH.
  `Repo.mk` exports `PATH` as the locked `.venv/bin`, then the inherited
  PATH, then `build/uv-bootstrap/bin`: a uv already on PATH still wins, and
  the bootstrap's python and pip never shadow the venv's.
- **`repo-suite-base` makes the ADR-101 merge-base resolvable.** It runs
  first in `repo-validate`. It honours a caller-set `L9_SUITE_BASE_REF` only
  if that ref already has a merge-base with `HEAD`; does nothing when the
  default base already resolves; otherwise fetches `refs/heads/main` from
  origin into `refs/remotes/origin/main`, unshallowing a shallow checkout,
  and checks again. A failed fetch or a base still without a merge-base
  fails with the reason. It never substitutes `HEAD` and never skips the
  comparison. Without a git work tree it defers to
  `scripts/validate_release.sh`, which records the base as `UNRESOLVED`.
- **`L9_SUITE_PROFILE ?= local`.** Core's runner provides no PostgreSQL,
  Redis or semantic authority; V-001 admits those skips only under the
  repository's declared `local` profile. `L9_SUITE_PROFILE=ci` selects the
  strict verdict where the services exist. CI's own run is unchanged.

## Alternatives Considered

1. Ask Core to move this repository back to `migration` mode.
2. Write a V1 contract with command matrices.
3. Have `repo-validate` call only `scripts/validate_release.sh`.
4. Rewire `ci.yml` to call the `make` phases in the same change.
5. Treat an unresolved suite base on Core's runner as acceptable.

## Rejected Alternatives

1. The enforcement mode is Core policy, and moving back only defers the
   migration.
2. Required mode refuses V1.
3. That drops CI's static gates and the separate active-memory step from the
   phase Core treats as validation.
4. `.github/workflows/**` belonged to a parallel lane, and two moving parts
   in one change hide which one broke.
5. V-001 then ends unknown, which is not a pass (ADR-101); substituting
   `HEAD` for the base would make the removed-test comparison vacuous.

## Invariants

1. `Makefile` equals Core's `make-v1` facade byte-for-byte; repository
   recipes live only in `Repo.mk`.
2. The `Repo.mk` leaves run what CI's `validate` job runs. A gate added to or
   removed from one is added to or removed from the other.
3. No phase skips because another phase passed. No stamp files.
4. The alignment scan judges this repository's files and only those.
5. The suite base is either the real merge-base with `origin/main` (or a
   caller-set base) or the run fails or records `UNRESOLVED`; it is never
   `HEAD`.

## Consequences

- `Analyze (central Core)` reported success on the final head of #120
  (`96f6f3e`), which unblocked merges in this repository.
- Core runs the full pytest suite twice per run (inside
  `validate_release.sh` and in `test`) and the assurance validators twice in
  `validate`. This is deliberate: each phase is its own process and a
  skip-by-stamp is forbidden by `l9.contract/validation-and-correctness@1`.
- `Repo.mk` can drift from `ci.yml`; its header names the mapping so review
  can catch drift.
- `repo-validate` may fetch from origin when the base is absent, so a Core
  run needs read access to the repository's `main`.

## Security Impact

None to runtime. `repo-setup` installs uv from PyPI into an untracked
`build/uv-bootstrap` only when uv is absent; the version is unpinned, matching
CI's `setup-uv`, and `UV_VERSION` pins one. `repo-suite-base` fetches only
`refs/heads/main` from the configured origin. No secret is read or written.

## Migration Impact

None to the package, its schema or its stores. Developers gain
`make setup|check|test|validate`; bare `make` prints help, and
`bash scripts/validate_release.sh` still works on its own.

## Validation Requirements

- Core's `run-repository-verification` reports
  `repository verification: PASS (required; v2; setup + validate + check + test)`;
  `Analyze (central Core)` is the required check that runs it.
- Core's `tools.l9_repo validate` passes the facade bytes and the `Repo.mk`
  ABI.
- The alignment-scan tests prove an injected `.l9/runtime` tree produces no
  finding with and without a work tree, while the same text in tracked,
  untracked and repository-tracked `.l9/runtime` files still does.
- `make validate` ends `PASS` locally.

## Rollback Conditions

Revert `Makefile`, `Repo.mk`, `.l9/repo-workflow.json` and the allowlist
entries if Core changes the contract or the facade, or if a phase cannot pass
on Core's runner. Reverting restores the required-mode `FAIL` on every pull
request.

## Supersedes / Superseded By

Supersedes: nothing. Amends the top-level allowlist ADR-099 retained by two
entries (`Makefile`, `Repo.mk`). Superseded by: nothing.
